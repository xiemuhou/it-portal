# IT 门户数据库迁移与完整恢复手册

> 本文主要保留现有Windows/SQL Server环境的迁移与恢复方法。迁往Linux/MySQL时，请使用[Linux快速部署手册](Linux快速部署手册.md)。SQL Server `.bak`不能直接导入MySQL，必须先恢复到SQL Server后再运行跨数据库迁移工具。

本文适用于以下情况：

- SQL Server 地址、账号或数据库名改变；
- 将 `itPortal` 迁移到新的 SQL Server；
- 门户服务器重装或迁移；
- 数据库故障后，从 `.bak` 和门户文件恢复系统。

> 当前版本尚未提供“一键生成单文件门户恢复包”。现阶段完整恢复必须同时准备 SQL Server `.bak`、整个 `data/business/` 目录和 `business.local.json`。不要逐个挑选知识库、附件和密钥文件，直接复制整个业务目录最不容易遗漏。

## 1. 先判断属于哪种迁移

### 1.1 只修改数据库地址

如果数据库本身没有迁移，只是服务器 IP、DNS 名称、端口或登录账号改变：

1. 执行 `portal.bat stop`。
2. 备份原 `business.local.json`。
3. 修改 `business.local.json` 的数据库地址、端口和账号。
4. 执行 `portal.bat deploy`，验证连接并检查迁移版本。
5. 执行 `portal.bat start` 和 `portal.bat status`。

这种情况不需要恢复 `.bak`，也不需要移动 `data/business/`。

### 1.2 将数据库迁移到新的 SQL Server

需要执行本手册第 2～6 节：停止门户、生成 `.bak`、复制整个业务目录、在新 SQL Server 恢复、修改配置并验收。

### 1.3 门户服务器和数据库服务器同时迁移

除数据库 `.bak` 外，还必须把整个 `data/business/` 和 `business.local.json` 安全传输到新门户服务器。不要复制旧 `.venv`，应在新服务器运行 `portal.bat deploy` 重新创建环境。

## 2. 迁移包应该包含什么

建议在受控存储中建立一个批次目录：

```text
ITPortal-Migration-YYYYMMDD-HHMM/
├─ database/
│  └─ itPortal-YYYYMMDD-HHMM.bak
├─ application/
│  └─ data/
│     └─ business/                 整个目录原样复制
├─ configuration/
│  └─ business.local.json          仅供恢复和修改，不得公开
└─ manifest/
   ├─ database-information.txt
   └─ sha256.csv
```

整个 `data/business/` 已包含：

- 知识库原文件；
- 公告和工单附件；
- HTML 知识资源；
- Wi-Fi、设备、线路和 IT 备忘录的加密根密钥；
- AI API 加密根密钥及密文文件；
- 文件一致性报告、迁移备份和运行日志。

为了降低漏备份风险，首次迁移建议全部复制。确认恢复流程稳定后，才考虑按保留策略排除可重建缓存或过期日志。

## 3. 在原服务器生成迁移材料

### 3.1 停止门户

```bat
cd /d "D:\04-AI Project\it-portal"
portal.bat status
portal.bat stop
```

停止后再复制本地文件，避免数据库记录和附件写入时间不一致。

### 3.2 生成 SQL Server 原生完整备份

由 DBA 使用 SSMS 或批准的备份任务执行完整备份。备份应使用 `COPY_ONLY` 和 `CHECKSUM`，并保存到数据库服务器之外的受控备份存储。

门户不提供数据库备份入口。由 DBA 使用 SQL Server Agent、维护计划、SSMS 或企业备份平台生成 `.bak`，并将文件复制到上述迁移批次的 `database/` 目录。

备份完成后由 DBA 执行：

```sql
RESTORE VERIFYONLY
FROM DISK = N'<备份文件完整路径>'
WITH CHECKSUM;
```

`RESTORE VERIFYONLY` 检查通过，只说明备份结构和校验信息可以读取，不等同于完整恢复演练。正式上线前仍应在隔离 SQL Server 上实际恢复一次。

### 3.2.1 使用 SSMS 配置日常自动备份

> 本节用于日常备份，不是第 3.2 节的一次性迁移备份。日常完整备份不要启用 `COPY_ONLY`，否则后续差异备份不能以它作为正常基准。当前 `itPortal` 使用 `FULL` 完整恢复模式，必须同时配置完整备份和事务日志备份。

#### A. 准备备份目录和权限

建议在数据库服务器创建以下目录：

```text
D:\SQLBackup\itPortal\Full
D:\SQLBackup\itPortal\Log
D:\SQLBackup\itPortal\MaintenanceLogs
```

目录应优先放在独立磁盘、NAS 或企业备份存储，不要只保留在 SQL Server 数据文件所在磁盘。至少还要将备份异机复制一份，避免数据库服务器或本地磁盘整体损坏后备份同时丢失。

在 Windows 中右键 `D:\SQLBackup`，依次进入“属性 → 安全 → 编辑 → 添加”，为下列服务账号授予“修改、读取、写入、列出文件夹内容”权限，并让权限应用到子文件夹：

```text
NT SERVICE\MSSQLSERVER
NT SERVICE\SQLSERVERAGENT
```

如果实例是命名实例，实际服务账号可能不同，应在“SQL Server 配置管理器 → SQL Server 服务”中确认。备份文件由 SQL Server 服务写入，维护计划和报告由 SQL Server Agent 执行；当前登录 Windows 的管理员能访问目录，并不代表这两个服务账号也能访问。

#### B. 创建每天完整备份计划

1. 打开 SSMS，连接 SQL Server。
2. 展开“管理 → 维护计划”，右键选择“维护计划向导”。
3. 在“选择计划属性”页面填写：
   - 名称：`ITPortal_每日完整备份`；
   - 运行身份：`SQL Server 代理服务帐户`；
   - 选择“整个计划使用单一计划”；
   - 点击“更改”，设置为每天 `02:00` 执行并启用计划。
4. 在“选择维护任务”页面勾选：
   - “备份数据库（完整）”；
   - “维护清理任务”。
5. 确认任务顺序为“备份数据库（完整）→ 维护清理任务”。
6. 在“定义备份数据库（完整）任务”页面设置：
   - 数据库：选择“这些数据库”，只勾选 `itPortal`；
   - 备份组件：数据库；
   - 备份目标：磁盘；
   - 选择“为每个数据库创建备份文件”；
   - 文件夹：`D:\SQLBackup\itPortal\Full`；
   - 文件扩展名：`bak`；
   - 勾选“验证备份完整性”；
   - 启用备份压缩；
   - 不勾选 `COPY_ONLY`；
   - **绝对不要勾选“备份日志尾部并使数据库保持正在还原状态”**。
7. 在“维护清理任务”页面设置：
   - 文件类型：备份文件；
   - 文件夹：`D:\SQLBackup\itPortal\Full`；
   - 文件扩展名：`bak`，不要写成 `.bak`；
   - 删除早于：建议 `30` 天；
   - 目录与完整备份的实际输出目录必须一致。
8. 检查向导摘要并完成创建。

#### C. 创建事务日志备份计划

再次运行“维护计划向导”，建立独立计划：

1. 名称填写 `ITPortal_事务日志备份`。
2. 设置为每天运行，每 `30` 分钟执行一次，时间范围为 `00:00`～`23:59`。
3. 选择“备份数据库（事务日志）”和“维护清理任务”。
4. 事务日志备份设置：
   - 数据库：`itPortal`；
   - 文件夹：`D:\SQLBackup\itPortal\Log`；
   - 文件扩展名：`trn`；
   - 勾选“验证备份完整性”；
   - 启用备份压缩；
   - 不选择尾日志备份或恢复状态选项。
5. 日志清理任务设置：
   - 文件夹：`D:\SQLBackup\itPortal\Log`；
   - 文件扩展名：`trn`；
   - 删除早于：建议 `14`～`30` 天。

事务日志备份不是门户运行日志。它保存两次完整备份之间的数据变更，可将数据库恢复到误删或故障之前的具体时间，并让已备份的事务日志空间可以重新使用。第一次事务日志备份前，必须先成功完成一次正常完整备份。

如果日志备份只保留 14 天，则只有最近 14 天具备较完整的时间点恢复能力；如需保留 30 天的时间点恢复能力，完整备份和日志备份均应至少保留 30 天，并保证恢复所需的日志链没有缺失。

#### D. 修改自动清理、计划时间和报告目录

1. 在 SSMS 中展开“管理 → 维护计划”。
2. 右键对应维护计划，选择“修改”。
3. 双击“维护清理任务”，可以修改清理目录、文件扩展名和保留天数。
4. 修改执行时间时，在设计页面修改对应子计划的计划属性。
5. 修改执行报告目录时，在设计页面空白处右键，选择“报告和日志记录”或“日志记录和报告”，将文本报告目录改为：

```text
D:\SQLBackup\itPortal\MaintenanceLogs
```

6. 如果设计页面没有该入口，检查“SQL Server 代理 → 作业 → 对应维护计划作业 → 属性 → 步骤 → 编辑 → 高级”中的输出文件设置。
7. 修改完成后按 `Ctrl + S` 保存。

如需自动清理维护计划的文本报告，可在其中一个维护计划中再增加一个“维护清理任务”，文件类型选择“维护计划文本报告”，目录选择 `D:\SQLBackup\itPortal\MaintenanceLogs`，扩展名填写 `txt`，建议删除早于 90 天的报告。只需配置一处，避免两个计划重复清理同一目录。

维护计划执行报告只是任务运行记录，不是 `.bak` 数据库备份，也不是 `.trn` 事务日志备份，可以单独设置保留和清理策略。

#### E. 首次运行和日常检查

维护计划创建完成后，不要等到第二天再判断是否有效：

1. 展开“SQL Server 代理 → 作业”。
2. 找到维护计划生成的作业，先手动运行完整备份作业。
3. 确认 `Full` 目录生成新的 `.bak` 文件。
4. 完整备份成功后，再手动运行事务日志备份作业。
5. 确认 `Log` 目录生成新的 `.trn` 文件。
6. 右键作业选择“查看历史记录”，确认所有步骤均成功；任务显示成功但目录没有文件时，应重点检查实际输出路径和 SQL Server 服务账号的目录权限。
7. 对新的完整备份执行：

```sql
RESTORE VERIFYONLY
FROM DISK = N'D:\SQLBackup\itPortal\Full\<实际备份文件名>.bak'
WITH CHECKSUM;
```

8. 每季度至少在隔离实例进行一次真实恢复演练。验证完整时间点恢复时，应按“完整备份 → 可选差异备份 → 后续所有事务日志备份”的顺序恢复，日志文件必须连续且顺序正确。

#### F. 建议的运行基线

| 项目 | 建议配置 |
|---|---|
| 完整备份 | 每天 02:00，保留 30 天 |
| 事务日志备份 | 每 30 分钟，保留 14～30 天 |
| 数据库完整性检查 | 每周一次，避开业务高峰 |
| 备份校验 | 每次启用完整性验证，并定期执行 `RESTORE VERIFYONLY` |
| 真实恢复演练 | 每季度至少一次 |
| 异机副本 | 至少一份，不与数据库数据文件位于同一故障域 |

SQL Server 数据库备份不包含门户服务器上的 `data/business/`、`business.local.json`，也不包含 SQL Server 实例级登录名、SQL Server Agent 作业和服务器配置。应另外按照本手册第 2、3.3 和 3.4 节备份门户文件、配置及校验清单，并由 DBA 导出或记录实例级对象。

### 3.3 复制整个业务目录

可使用资源管理器复制，也可以使用 `robocopy`。下面命令只复制，不会删除目标目录已有文件：

```bat
robocopy "D:\04-AI Project\it-portal\data\business" "E:\ITPortal-Migration\application\data\business" /E /COPY:DAT /DCOPY:DAT /R:2 /W:2 /XJ
```

`robocopy` 返回码 0～7 通常表示复制完成或存在可接受差异，8 及以上表示失败，需要检查输出。不要使用 `/MIR`，因为它可能删除目标目录中已有文件。

然后复制配置文件：

```bat
copy "D:\04-AI Project\it-portal\business.local.json" "E:\ITPortal-Migration\configuration\business.local.json"
```

这些文件包含数据库密码和加密根密钥，禁止放入普通网盘、邮件附件或未加密 ZIP。应使用 BitLocker 加密磁盘、公司批准的加密文件传输或带 AES-256 加密的归档工具。

### 3.4 生成文件校验清单

在 PowerShell 中执行：

```powershell
Get-ChildItem 'E:\ITPortal-Migration' -Recurse -File |
    Get-FileHash -Algorithm SHA256 |
    Select-Object Path, Hash |
    Export-Csv 'E:\ITPortal-Migration\manifest\sha256.csv' -NoTypeInformation -Encoding UTF8
```

将迁移批次复制到其他介质后重新计算哈希，确认 `.bak`、附件和密钥没有损坏。

## 4. 在新 SQL Server 恢复数据库

### 4.1 恢复前要求

- 目标 SQL Server 版本必须与源版本相同或更高；
- 不支持将 SQL Server `.bak` 直接恢复到 MySQL；
- 优先恢复为新的数据库名，验证完成后再切换门户；
- 不要直接覆盖仍在运行的正式数据库；
- 如果备份使用 TDE 或备份加密，还必须先恢复对应证书和私钥。当前 `itPortal` 没有启用 TDE，但以后启用后必须更新本手册。

### 4.2 使用 SSMS 恢复

1. 打开 SSMS，连接目标 SQL Server。
2. 选择“数据库 → 还原数据库”。
3. 来源选择“设备”，添加 `.bak`。
4. 在“文件”页面确认数据文件和日志文件的新路径。
5. 建议先恢复为 `itPortal_RestoreTest` 等临时名称。
6. 完成后执行 `DBCC CHECKDB`。

```sql
DBCC CHECKDB (N'itPortal_RestoreTest') WITH NO_INFOMSGS;
```

恢复验证完成后，由 DBA 按变更流程确定正式数据库名。需要使用 `WITH MOVE` 或覆盖现有数据库时，必须由 DBA 根据 `RESTORE FILELISTONLY` 的结果编写命令，不能直接复制示例覆盖生产库。

### 4.3 创建门户数据库账号和权限

SQL Server 登录名属于实例级对象，不在 `itPortal.bak` 中。需要在新实例创建门户登录名，再映射到恢复后的数据库。

项目的 `scripts/grant-itportal-deployment.sql` 是部署授权参考，示例登录名为 `itportal_app`。正式环境应由 DBA 使用实际专用账号替换示例登录名后执行，并在迁移完成后回收不需要的建表和结构修改权限。

## 5. 在门户服务器恢复本地文件

### 5.1 安装代码和依赖

在新门户服务器放置相同版本的项目代码，然后执行：

```bat
portal.bat deploy
```

如果此时还没有正确的数据库配置，脚本会生成配置模板并停止，这是正常现象。不要启动门户。

### 5.2 恢复业务目录

确保门户处于停止状态，将迁移包中的整个 `application/data/business/` 复制到：

```text
D:\04-AI Project\it-portal\data\business\
```

目标 Windows 运行账号必须具有该目录的读取、创建、修改和删除权限。恢复后重点确认以下文件存在：

```text
data/business/wifi-secrets.key
data/business/ai-secrets.key
data/business/credentials/
data/business/attachments/
data/business/knowledge/
data/business/knowledge-assets/
```

不要在门户首次启动后才覆盖密钥；如果系统已生成新的空白密钥，必须停止服务并恢复原密钥，否则数据库中的历史密文无法解密。

### 5.3 恢复并修改配置

把迁移包中的 `business.local.json` 作为参考恢复，但必须修改：

- 新 SQL Server 地址和端口；
- 正式数据库名；
- 新数据库登录账号和密码；
- ODBC Driver 名称；
- SQL Server 证书验证设置；
- EHR、LDAP、AI和网络运维态势地址是否仍适用于新环境。

不要因为复制了旧配置就继续连接旧数据库。

## 6. 完成切换

```bat
portal.bat deploy
portal.bat start
portal.bat status
```

原生数据库恢复会带回尚未过期的历史登录会话。建议切换前由 DBA撤销所有旧会话：

```sql
USE [itPortal];
UPDATE dbo.user_sessions
SET revoked_at = SYSUTCDATETIME()
WHERE revoked_at IS NULL;
```

执行后所有用户需要重新登录。

## 7. 恢复验收清单

至少检查以下项目：

- `portal.bat status` 显示监听、受管和健康状态均正常；
- 管理员和普通员工可以重新登录；
- 公告列表及公告附件可以打开、下载；
- 工单、留言和工单附件完整；
- 知识库 HTML、PDF、PPT/PPTX 可以阅读；
- VLAN、Wi-Fi、网络设备、带宽线路和 VPN 隧道记录完整；
- Wi-Fi、设备、线路和 IT 备忘录的历史密码可以正常解密；
- AI助手配置仍可执行连接测试；
- 静态 IP、电脑设备、耗材及其关联关系完整；
- 部门、人员、账号、角色和权限完整；
- 文件一致性巡检没有缺失文件、哈希不一致或异常孤立文件；
- EHR和LDAP连接测试只读且正常。

验收完成前不要删除原数据库、原 `data/business/` 或原迁移批次。

## 8. 回滚方法

如果新环境验证失败：

1. 执行新环境的 `portal.bat stop`。
2. 保留失败环境的数据库和日志用于排查，不要覆盖原备份。
3. 将 DNS、反向代理或访问地址切回旧门户服务器。
4. 确认旧门户仍连接旧数据库和原业务目录。
5. 执行旧环境的 `portal.bat start` 和 `portal.bat status`。

如果迁移期间允许用户继续在旧系统操作，切换前必须重新生成最终数据库备份和文件快照，否则迁移开始后新增的数据不会出现在新系统中。最稳妥的方式是在最终备份和复制期间设置维护窗口并停止门户。

## 9. 关于未来的一键恢复包

未来可以将数据库逻辑导出、整个 `data/business/`、配置和哈希清单生成一个经过密码加密的下载文件，并提供离线恢复命令。但它属于“门户级恢复包”，不能替代 SQL Server 原生全量、差异和事务日志备份。

门户不承担数据库备份和恢复职责；即使未来增加系统文件打包功能，也不能替代 SQL Server 原生完整、差异和事务日志备份。
