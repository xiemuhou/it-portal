## 1. 结论

系统当前适合作为公司内部、小到中等并发规模的单机门户继续试运行。业务边界、权限校验、乐观锁、工单幂等、台账关联、EHR 只读同步和跨 SQL Server/MySQL 的逻辑模型已经形成，82 项自动化测试全部通过。当前数据库实际规模很小，暂未出现容量或查询性能瓶颈。

上线前仍有 4 类基础能力需要补齐：数据库与附件的统一备份及恢复演练、应用与数据库错误日志、真实健康检查、文件写入与数据库事务的一致性。它们不会改变现有页面和业务流程，但直接决定故障后能否定位问题及恢复数据。

随着数据增长，最先需要优化的路径预计是公告通知批量写入、用户和电脑列表的 N+1 查询、EHR 全量逐行同步、工单报表全量加载，以及审计日志和通知表的长期增长。当前规模不需要提前重构主键或分库分表。

## 3. 风险与建议

### P0：上线前必须完成

#### P0-1 数据库和文件没有形成可验证的统一恢复闭环

**证据：** SQL Server 当前为 FULL 恢复模式，`msdb` 中未查询到 `itPortal` 的备份历史。应用提供 `BACKUP DATABASE ... COPY_ONLY, CHECKSUM`，但该备份只覆盖数据库；知识库、公告附件、工单附件和凭据加密密钥位于本地文件系统。应用数据目录的 `backups` 当前为空。

**影响：** 数据库故障、主机磁盘损坏或误删时，可能只能恢复数据库记录而无法恢复附件；丢失加密密钥会使已保存的网络凭据无法解密。FULL 模式如果长期没有事务日志备份，还可能导致日志文件持续增长。

**建议：**

1. 由 SQL Server 运维建立正式的全量、差异和事务日志备份计划；若业务不需要时间点恢复，应由 DBA 明确评估是否改为 SIMPLE，而不是长期保留无日志备份的 FULL。
2. 同一备份批次包含数据库、`data/business/attachments`、`knowledge`、知识预览缓存的重建规则，以及加密密钥。密钥应单独加密保管并限制访问。
3. 为每个批次生成清单，记录数据库备份时间、文件快照时间、文件数量、总大小和哈希。
4. 在隔离环境完成一次完整恢复演练，验证登录、附件打开、知识库阅读、加密字段解密、工单和台账关联。

**验收标准：** 恢复演练文档记录 RPO/RTO；随机抽取的数据库记录、附件和加密字段全部可用；SQL Server 备份历史可查；备份失败有告警。

### P1：建议首个上线迭代完成

#### P1-1 文件系统与数据库事务存在不一致窗口

知识库、公告附件和工单附件先写本地文件，再写数据库。数据库事务失败会留下孤立文件；删除路径中也存在数据库提交与文件删除无法原子完成的情况。

建议采用“临时文件 → 数据库记录 pending → 提交 → 原子重命名 → ready”的状态流程，并增加每日孤立文件与缺失文件核对任务。短期可以先增加只读巡检和清理报告，不改变用户操作流程。

#### P1-2 可观测性不足，数据库故障对用户可见但对管理员不可诊断

建议增加结构化日志，至少包含请求 ID、接口、用户 ID、耗时、状态码、异常类别和数据库错误编号，严禁记录密码、Cookie、连接串和文件正文。将 `/api/health` 分为存活检查与就绪检查：存活仅判断进程，就绪执行轻量 `SELECT 1`、数据目录读写或空间检查，并显示 EHR 最近同步状态。为 5xx、数据库连接池耗尽、同步失败、备份失败和磁盘低空间建立告警。

#### P1-3 当前部署只能安全地按单应用实例理解

EHR 调度器和同步锁位于应用进程内。定时同步使用数据库唯一键避免同一天重复执行，能降低多进程重复同步风险；手动同步使用随机触发键，多进程或多主机下仍可能并行执行。附件保存在本机磁盘，也限制了横向扩容。

建议短期保持单应用实例，并用 Windows 服务、NSSM 或计划任务实现自动启动和崩溃拉起；前置 IIS/Nginx/Caddy 提供 HTTPS、请求大小限制和访问日志。以后扩展为多进程或多主机前，将任务锁改为 SQL Server 应用锁或任务表抢占，并将文件迁移到共享存储或对象存储。

#### P1-4 EHR 同步为全量读取和逐行查询/更新

同步会把三个视图全部读入内存，随后对部门、人员、岗位和任职逐条查询及写入。当前 466 用户可以接受；当人员达到数千至数万时，事务时间、锁持有时间和密码哈希 CPU 开销会明显增加。进程异常退出还可能留下 `running` 状态的同步记录。

建议先记录每次读取条数、应用条数、耗时和错误数。第二阶段改为暂存表加集合式 `MERGE`/批量 upsert，或使用 `executemany` 分批处理；同步事务按实体或批次控制。启动时识别超过阈值的 `running` 任务并标记为中断。EHR 查询继续保持专用只读账号和固定 SELECT 白名单。

#### P1-5 依赖版本范围较宽，缺少可复现部署清单

依赖文件使用大版本范围，例如 FastAPI `<1`、SQLAlchemy `<2.1`。重新安装时可能获得与测试环境不同的小版本，造成上线结果不一致。

建议保留开发范围文件，同时生成经验证的锁定清单，记录 Python、ODBC Driver、LibreOffice/PowerPoint 转换组件和操作系统版本。升级依赖时由自动化测试和预发布环境验证后再更新锁定文件。

### P2：数据增长后按阈值实施

#### P2-1 列表与权限查询存在 N+1

- 用户列表每页先取用户，再逐人查询角色和岗位；50 条一页时会额外产生约 100 次查询。
- 工单处理人下拉会读取全部启用用户，并对每个用户单独计算 `ticket.claim` 权限。
- 电脑列表先取 ID，再逐台查询网卡、配件和关联 IP。

建议用一次批量查询取回当前页所有角色、岗位、网卡、配件和 IP，再按 ID 在内存组装；处理人列表可直接通过角色与权限关系集合查询。验收时记录 SQL 次数，目标是每个列表接口不随页内记录数线性增加。

#### P2-2 公告发布按用户逐条写通知

当前 357 个启用用户会产生 357 条通知，仍可接受。达到 2,000～5,000 用户后，逐条插入会延长公告发布事务和锁持有时间。

建议改为批量插入并按 500～1,000 条分批，或发布公告后写入后台分发任务。必须保留 `(recipient_user_id, event_key)` 唯一约束，确保重试不重复通知。

#### P2-3 报表在应用内加载全部周期后汇总

工单报表未指定日期时会加载所有已关闭处理周期，并在 Python 中汇总；处理分段再按每 500 个周期查询。数据达到数十万周期时会增加数据库传输量和进程内存。

建议默认限定最近 90 天，允许用户明确选择更长范围；分类、处理人、状态和时长统计尽量使用 SQL `GROUP BY`。当 `ticket_cycles` 达到 50,000 行或接口 P95 超过 1 秒时实施。

#### P2-4 OFFSET 深页分页和 `%关键词%` 搜索最终会退化

用户、工单、知识库、公告、审计等列表使用 OFFSET；模糊搜索使用前后通配符。当前最多 807 行没有实际问题。审计日志、通知和工单超过 100,000 行后，深页和全文模糊搜索会逐渐变慢。

建议先为审计和通知定义保留周期与归档策略；高增长列表改为基于时间和 ID 的游标分页。只有在真实慢查询证明需要时，再考虑 SQL Server Full-Text/MySQL FULLTEXT 或专用搜索字段。

#### P2-5 导出和知识推荐存在固定内存上限路径

通用导出一次读取最多 50,001 行并在内存生成 XLSX；知识推荐最多载入 1,000 篇文章后在 Python 扫描关键词。建议大导出改为后台任务或流式生成，并要求筛选范围；知识文章超过 1,000 篇前引入数据库全文索引或独立检索服务。

#### P2-6 历史表缺少明确保留策略

审计日志、站内通知、IP 历史、电脑变更历史和同步运行记录会持续增长。建议业务审计记录按公司合规要求长期保存并按年度归档；已读通知可保留 180～365 天；同步运行明细可保留 180 天；IP/电脑变更历史按资产生命周期保留。删除或归档任务必须先形成报表并经过业务确认。

### P3：长期演进项

- UUIDv7 字符串主键当前可维护且性能足够。未来新建亿级事件表时，可评估 `BINARY(16)` 或内部 `BIGINT` 加公开 UUID；现有表不建议为理论收益重构。
- 知识库每次阅读同步更新 `view_count`，高访问量时会形成热点行。单篇文章每秒达到数十次读取后，可改为异步计数或按分钟合并。
- 清理旧原型入口、历史 README 描述和未使用表定义，减少维护人员误启动 8088 原型或误判真实数据源。清理前应确认无外部脚本依赖。

## 4. 容量与性能基线

建议从上线首日开始采集以下指标，以 30 天数据替代当前推测：

| 指标 | 建议目标或告警阈值 |
|---|---|
| 常用列表 API | P95 < 500 ms，P99 < 1 s |
| 普通新增/修改 | P95 < 1 s，不含大文件转换 |
| 数据库连接池等待 | P95 < 100 ms；出现超时立即告警 |
| 5xx 比例 | 5 分钟窗口 > 1% 告警 |
| EHR 同步 | 5,000 人规模 < 5 分钟；失败立即告警 |
| 公告通知分发 | 5,000 用户 < 10 秒，或转后台任务 |
| 磁盘可用空间 | < 20% 预警，< 10% 严重告警 |
| SQL Server 日志使用率 | 持续 > 70% 告警并检查日志备份链 |
| 备份恢复 | 至少每季度恢复演练一次 |

连接池不应直接按默认值上线。应先按实际同时在线人数压测，再设置 `pool_size`、`max_overflow`、`pool_timeout`、`pool_recycle` 和数据库命令超时。单进程内部系统可从较小池开始，避免应用连接数挤占 SQL Server；参数必须可配置并有监控。

## 5. SQL Server 到 Linux/MySQL 的兼容性

总体可迁移，但当前不能视为已经验证完成。

已经具备的基础包括：SQLAlchemy 统一模型、MySQL `utf8mb4`、跨数据库日期类型变体、UUID 字符串主键，以及 DDL 双目标编译测试。明显的 SQL Server 专用功能主要是网页数据库备份和 EHR 数据源连接，这两部分需要保留独立适配器。

迁移前需要在真实 MySQL 8 环境验证：

1. Alembic 从空库升级到最新版本，并从 SQL Server 抽样迁移数据。
2. `utf8mb4` 字符集、大小写和重音排序规则，尤其是账号、部门编码、MAC/IP 与唯一约束。
3. `DATETIME(3)` 的 UTC 约定及应用层时区转换。
4. 布尔值、长文本、唯一约束、外键删除顺序和事务隔离差异。
5. 36 字符 UUID 在所有二级索引中的空间开销；先保留现状，依据实际慢查询再调整。
6. MySQL 备份、恢复、主从复制和对象/共享文件存储方案。
7. Linux 上知识文档转换工具、中文字体、文件权限和服务账户权限。

建议把 MySQL 兼容验证作为独立预发布阶段，不要在首次正式上线时同时更换操作系统和数据库。

## 6. 分阶段实施计划

### 阶段 A：上线前，预计 2～4 个工作日

- 建立数据库、附件和密钥的统一备份方案并完成恢复演练。
- 增加结构化错误日志、真实就绪检查、磁盘和备份告警。
- 固定依赖版本，形成服务器安装清单和回滚步骤。
- 将应用注册为受守护的系统服务，并通过反向代理提供 HTTPS。

**回滚：** 监控和反向代理可通过切回原启动入口回滚；备份策略只增加保护，不修改业务表。

### 阶段 B：上线后 1～2 个迭代

- 修复文件与数据库一致性窗口，增加孤立文件巡检。
- 合并用户、处理人和电脑列表的 N+1 查询。
- 公告通知改为批量插入；EHR 同步增加指标和中断任务处理。
- 根据实际查询计划仅添加必要索引。每个索引上线前记录查询、逻辑读和写入开销。

**回滚：** 保留旧查询实现或功能开关；新增索引可单独删除；文件状态改造需先兼容旧 `ready` 记录。

### 阶段 C：达到增长阈值后

- 报表改为数据库聚合，审计和通知改为游标分页及归档。
- EHR 改为暂存表和集合式同步。
- 大导出改后台任务，知识推荐接入全文检索。
- 若需要多实例部署，再引入分布式任务锁和共享文件存储。
